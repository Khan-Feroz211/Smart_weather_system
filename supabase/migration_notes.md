# SQLite → Supabase migration notes

Supabase PostgreSQL is now the **only** database the application reads and writes.
`smart_weather.db` is kept as a read-only backup / migration source — the app never opens it.

## 1. Architecture (and why)

| Concern | Choice | Reason |
|---|---|---|
| Data access | Direct PostgreSQL connection (`SUPABASE_DB_URL`, pooled psycopg2 in `db.py`) | The app runs ~150 hand-written SQL statements (joins, `GROUP BY`, `AVG`, transactions). The Supabase REST client cannot express these. The connection string is a backend secret, exactly like the service-role key. |
| Login | Supabase Auth via its REST API (`supabase_client.py`, `requests`) | No plaintext passwords anywhere; no extra `supabase` package needed. |
| Authorisation | Server-side, re-checked from the database on **every** request (`auth.py`) | Session cookie only holds the profile UUID. Role / active flag / `admin_users` row are read fresh each time. |
| RLS | Enabled on all 27 tables (`schema.sql` §9) | Protects the public Supabase REST API (anon key). The Flask backend connects as the database owner and enforces its own rules. |

Because the backend connects as the owner role it bypasses RLS by design; RLS exists so that the
**anon/authenticated browser keys can never read or write anything they should not**.

## 2. Table mapping

All 20 original tables were migrated, plus 5 that the code creates lazily
(`experiments`, `model_versions`, `dataset_versions`, `multi_hazard_alerts`, `hazard_probabilities`)
and 2 new ones (`admin_users`, `admin_audit_log`).

| SQLite | PostgreSQL | Notes |
|---|---|---|
| `users.user_id INTEGER` | `users.id uuid` **+** `users.user_number bigint` | Old ids are preserved in `user_number`, so `/user/<int>` URLs and templates keep working. New columns: `auth_user_id, role, is_active, is_online, updated_at, last_seen_at, last_login_at, login_count`. |
| `TEXT` JSON blobs | `jsonb` | `quality_flags, cleaning_notes, feature_blob, decision_blob, raw_payload, cleaned_payload, feature_payload, decision_payload, preferences, trigger_conditions, …`. The app still receives them as JSON *text*, so existing `json.loads()` calls are unchanged. |
| `TIMESTAMP` / ISO `TEXT` | `timestamptz` | Returned to Python as `'YYYY-MM-DD HH:MM:SS'` (UTC) strings, so templates that slice `created_at[:16]` still work. Free-form form dates (`planted_date`, `expected_harvest_date`, `recommended_date`) stay `text`. |
| `BOOLEAN` / `INTEGER` 0/1 | `boolean` | Queries changed from `is_active = 1` to `is_active`. |
| `AUTOINCREMENT` ids | `GENERATED BY DEFAULT AS IDENTITY` | Explicit ids can be inserted (migration / demo seed); sequences are re-synced afterwards. |
| `user_activities.user_id`, `weather_alerts.user_id` | `uuid` FK → `users(id)` | `ON DELETE CASCADE`. |
| agriculture tables | real foreign keys (`fields.farm_id → farms`, `crop_* .field_id → fields`, …) | `ON DELETE CASCADE`. `farms.created_by → users` added (nullable). |
| sensor tables | indexes only, **no FK on `field_id`** | Devices may report ids that are not registered fields yet; ingestion must never reject a reading. |

### Code changes worth knowing about
* `INSERT OR IGNORE/REPLACE` → `ON CONFLICT …`; `cursor.lastrowid` → `RETURNING`; `datetime('now', …)` → `now() - interval`; `strftime` → `EXTRACT`.
* `GROUP BY` with non-aggregated columns (allowed in SQLite) → `DISTINCT ON` (latest reading per sensor type).
* SQLite-only `PRAGMA` schema auto-migration was removed; the schema lives in `supabase/schema.sql`.
* `sensor_health` upsert no longer resets `uptime_percentage` / `calibration_date` on every reading (the old `INSERT OR REPLACE` did).
* JSON written to `jsonb` goes through `db.safe_json()` (NaN/Infinity/numpy/datetime safe).
* **Pre-existing bug fixed:** two functions named `clean_sensor_data` existed in `app_clean.py`; the Flask view replaced the pipeline helper, so the live weather pipeline crashed (this is why the SQLite file has 0 pipeline rows). The helper is now `clean_weather_record`.

## 3. Setup steps (in order)

1. **Create a project** at https://supabase.com/dashboard → *New project*. Save the database password.
2. **Run the schema:** dashboard → *SQL Editor* → paste `supabase/schema.sql` → *Run*. (Idempotent — safe to re-run.)
3. **Collect the values** (dashboard → *Project Settings*):
   * *API* → **Project URL** → `SUPABASE_URL`
   * *API* → **anon public** key → `SUPABASE_ANON_KEY`
   * *API* → **service_role** key → `SUPABASE_SERVICE_ROLE_KEY` (**secret — backend only**)
   * *Database → Connection string → Session pooler* → `SUPABASE_DB_URL` (replace `[YOUR-PASSWORD]`). Use the pooler string: the direct `db.<ref>.supabase.co` host is IPv6-only on many plans.
4. **Authentication settings** (*Authentication → Providers → Email*): keep *Enable email provider* on. Turn *Confirm email* on for production (recommended) — or off while testing.
5. **Configure `.env`** (copy `.env.example`). Generate a real `SECRET_KEY`:
   `python -c "import secrets; print(secrets.token_hex(32))"`
6. **Install:** `pip install -r requirements.txt`
7. **Migrate existing data (optional, do this BEFORE the first app start):**
   ```bash
   python scripts/migrate_sqlite_to_supabase.py --dry-run   # preview, needs no database
   python scripts/migrate_sqlite_to_supabase.py             # real run
   ```
   Re-runnable; prints a per-table report and target counts. Never modifies the `.db` file.
8. **Verify:** `python scripts/check_supabase.py` (env, tables, RLS, and every admin query is executed once).
9. **Create the first admin:** `python scripts/create_admin.py` (uses `ADMIN_EMAIL`, asks for a password twice, hidden).
10. **Run:** `python app_clean.py` (or `python start_app.py`) → http://localhost:8000 → admin at `/admin/login`.

If you skip step 7 the app seeds the same small demo data set it always did (`SEED_DEMO_DATA=false` disables that).

## 4. Legacy users
The old `users` table had no passwords or login — rows were plain profiles. They are migrated as
**profile-only** users (`auth_user_id IS NULL`). When that person later signs up with the same email and
confirms it, the profile is linked automatically (the link is deliberately refused for unconfirmed
emails so nobody can claim someone else's profile).

## 5. Rollback
Nothing was deleted. To go back: check out the previous version of the code and point it at `smart_weather.db`.
Data written to Supabase after the switch would not be in the SQLite file.

## 6. Security notes
* `.env` is git-ignored; `.env.example` is the committed template. Rotate any key that was ever committed.
* The service-role key and DB URL are read only in `supabase_client.py`, `db.py` and `scripts/`. A test
  (`tests/test_admin_security.py`) asserts they never appear in templates/static files or rendered pages.
* `SECRET_KEY`: the old hard-coded fallback was removed. A missing/weak key is refused unless `DEBUG=True`.
